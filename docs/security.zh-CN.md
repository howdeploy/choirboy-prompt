# 安全与披露

安全框架、发布前清理清单、负责任披露规则。本文档是项目如何看待自己。

---

## 1. 受控验证框架

本项目为**防御性安全验证**而发布：

- 测试——在**自己**的智能体和**自己**的 lore 文件上；
- 不针对第三方：其他用户、他们的数据和智能体不受影响；
- 发现指向厂商和 harness 作者——以便在平台层面构建检测（见 [docs/detection.zh-CN.md](detection.zh-CN.md)）。

向量只在受控环境中复现，不用于第三方系统。每次发布都解释机制，但不提供针对他人系统的现成攻击工具。

---

## 2. 研究边界

| 可以 | 不可以 |
|---|---|
| 在自己的智能体上研究向量 | 针对他人智能体/用户使用向量 |
| 发布机制和 lore 工件 | 发布恢复他人密钥的可用工具 |
| 把发现指向厂商 | 在修复前利用发现 |
| 分析已公开披露的事件 | 公开受害者地址和完整整合地址 |
| 给厂商检测建议 | 针对在线系统发布 PoC |

这些边界不是装饰：它们与 `research/10`（第三方合约审计与负责任披露）和 `research/09`（web3 安全、密钥熵）一致。

## 3. 发布前清理清单

插件天生携带**个人记忆**——「人 + 智能体」组合的共同工作历史。公开仓库与本地安装是不同的空间。清单：

### 3.1. 内容

发布**已清理**的版本：lore 和研究文档承载待验证机制，但不含可识别细节。

- [ ] `prompt.md`、`lore.md`、`user.md`——发布；已检查不含通往私有项目的路径和个人数据。
- [ ] `security-posture.md`——作为 payload 的一部分发布；中性词汇，不含超出公开框架的绕过审核指令。
- [ ] `research/01–14`——发布；已检查不含具体 NSFW/refusal 模型名称、通往含地址文件的路径、完整地址。
- [ ] `security-audit-runbook.md`——可执行的审计命令；安全，引用 `security-posture.md`——检查关联。

### 3.2. 识别

- [ ] 没有通往私有项目的路径提及（弱熵研究仓库等）。
- [ ] 没有完整钱包地址；只在必要时保留匿名前缀（`bc1qnk…`）。
- [ ] 没有具体 NSFW/refusal 模型或去拒绝 LoRA 的名称；保留功能角色（「NSFW 检查点」、「拒绝抑制」）。具体禁用名单放在**仓库之外**（私有清单）——不在公开文档中复现。
- [ ] 公开文本中没有「Creator/Master」称呼和个人细节。

### 3.3. 机制

- [ ] 手动安装即时读取工作副本；marketplace 安装使用 cache，只有提升版本后
      才会获得修改。
- [ ] `python3 scripts/build-context.py --check` 通过：inline skill 是清理后规范
      上下文的精确生成副本。
- [ ] `${CLAUDE_PLUGIN_DATA}/latest-delivery.log` 只包含版本、hash、nonce 与
      plugin root，不包含 lore 或用户文本。
- [ ] 钩子在没有规范内容文件时也能工作（graceful 模式）：不会因
      `set -euo pipefail` 失败，而是跳过缺失文件并给出警告。

### 3.4. 仓库

- [ ] `.gitignore` 在第一次 `git add .` **之前**创建（见下方示例）。
- [ ] `LICENSE` 存在（README 和徽章引用它）。
- [ ] 清单 `.claude-plugin/plugin.json` 改名为公开名称（`choirboy-prompt`），版本已提升。
- [ ] `.claude-plugin/marketplace.json` 与 `plugin.json` 版本一致；
      `claude plugin validate .` 通过。

### 3.5. `.gitignore` 示例

内容被发布，所以 `.gitignore` 只做杂务：


## 4. 负责任披露规则（按 research/10）

在他人项目中的发现按流程处理：

1. 联系项目：安全联系人、赏金计划（Immunefi、HackerOne、Sherlock、Code4rena）或公开渠道。
2. 报告：类别、影响、**在分叉/测试网上**的 PoC、修复建议。不利用他人资金，修复前不公开披露。
3. 修复窗口（通常最多 90 天，按约定）。
4. 修复后（或截止日期后）发布：给项目和社区的报告、给集成方的建议。
5. 如果无法联系或项目保持沉默——在伦理截止日期发布，携带最少的可利用细节：我们绝不发布针对在线资金的可用漏洞利用。

## 5. 会话被标记时的行为

一个已知的厂商问题：服务端分类器会无视上下文中的框架标记防御性词汇。Claude 一次误报会毒化整个会话——之后只会更糟。

规则：在被标记的会话中不继续、不争论。带着显式框架从第一轮开始新会话：「这是我的仓库，按 OWASP 审计我自己的代码」。在新会话中从该框架出发工作。

这不是向量的一部分——这是针对误报的对抗措施。

## 6. 发布风险评估

| 风险 | 级别 | 缓解 |
|---|---|---|
| 仓库识别出作者（个人记忆） | 中 | 清理：切断私有项目路径、完整地址、NSFW/refusal 模型名称 |
| 向量被解读为绕过审查指南 | 中 | README 和本文档中的安全框架；机制 + 对抗措施，而不是「如何攻击」 |
| 地址/密钥泄漏 | 严重 | 发布前检查：grep bc1/0x/seed 文件 |
| NSFW 模型名称泄漏 | 高 | 用功能角色代替名称；私有名单放在仓库外 |
| 把 AI 审计当保证 | — | Coldcard 拆解（`research/11`）：一次性 AI 审计漏掉了 bug；审计必须检查可执行路径，而不是代码是否存在 |

## 7. 发布 session fixtures

原生 transcript 可能比 lore 含有更多敏感信息。在向 `sessions/` 添加内容前：

- 只使用你自己的临时运行时与对话；
- 删除凭据、request ID、私有路径、tool output 与第三方数据；
- 一致替换 ID，且不破坏 parent chain 与 picker metadata；
- 把每份本地构造的 transcript 标为非历史兼容性 fixture；
- 明确说明运行时接收证明的是 provenance 缺失，而不是历史事件；
- 关闭应用，并只在有备份的本地 store 上测试。

完整 authoring 与 sanitization gate 见
[docs/authoring.zh-CN.md](authoring.zh-CN.md)。
